**Purpose.** Record where the requirements, plan and tests do not yet fully answer a question, where technical risk is high, and what is deliberately deferred. This file is a living register: each gap has an ID, a proposed resolution, a decide-by phase and a status. Gaps are closed here (never deleted) and the decision is copied to progress.md's decision log.

**Severity:** *Blocker* = must be resolved before the named phase can start or finish · *Major* = affects behaviour users will notice · *Minor* = detail or polish.

### Gaps found by spike S1 (2026-11-05)

| ID | Gap | Why it matters | Proposed resolution | Decide by | Severity | Status |
|---|---|---|---|---|---|---|
| **G-15** | **Quantum-snapped scheduling targets must use the engine's own clock arithmetic.** `SpessaSynthProcessor` advances its clock by `quantumFrames * (1 / sampleRate)` once per render quantum and *accumulates* the rounding error. The obvious `currentTime + quanta * (quantumFrames / sampleRate)` computes a different double that lands a few ULP above the clock the engine actually reaches; the engine's `event.time <= currentTime` test then fails and every event is dispatched a whole quantum (128 frames ≈ 2.7 ms) late. Measured in S1: 128.00 frames against 0.00 frames for the correct arithmetic. | Silent, uniform 2.7 ms lateness on every note. It is within the one-quantum budget, so it would pass a coarse test and still be wrong; it also breaks the bit-identical live/export comparison ADR-0002 relies on. | P4.6 must compute the snapped target with the engine's own accumulation — the spike's `engineClockAfterQuanta` (`spikes/s1/renderer/analysis.ts`) and its regression test are the reference. Keep the helper as the single place the arithmetic lives; never recompute it at a call site. | P4 | Major | **Open — P4.6.** ADR-0002 §2 records the rule; the helper and test exist in the spike. |
| **G-16** | **The S1 pass criterion "no dropouts for 10 minutes on a low-end laptop" is only half met.** The 10-minute soak ran on a recent thin-and-light laptop (Core 5 120U) and passed with 0 dropouts over 60 011 blocks at 9.28 % average process-tree CPU. The *low-end* clause is untested; the headroom is an inference, not a measurement. | The CPU budget in testing.md §8 ("under 25 % of one core") and the low-tier gate in testing.md §3 depend on it. A machine an order of magnitude slower would change the answer. | Run `pnpm run spike:s1:browser` (or `electron spikes/s1/electron/drive.cjs --soak 600`) on the oldest machine in the support matrix, and again on Linux (PulseAudio and PipeWire) and macOS. Record the result in `docs/test-runs/` and close the gap. | P1 | Major | **Open — measured on Windows only.** Tracked as `S1-LOWEND` in progress.md §5. |
| **G-17** | **The engine's effects chain is on by default and changes the sound.** S1 measured with `effectsEnabled: true` (the library default): reverb and chorus are applied, and the dry signal differs by **−42.6 dB**. The measurement harness does not model a dry-signal export, and the bundled fonts' presets may rely on the reverb tail to sound natural. | Export and live playback must agree with each other and with what the user hears (FR-SND-3). A dry export would sound different from live playback; a wet export would carry reverb into the audio file, which most users would not expect from a backing track. | Decide in P4 whether effects are on for live playback and for export, and make the two paths agree. If a dry signal is wanted, disable effects in *both* paths and re-measure the level and the offline/real-time equivalence — the S1 figures for effects-on do not carry over. | P4 | Major | **Open — product decision.** Recorded in ADR-0002 §"What was not decided here". |
| **G-18** | **The library's offline path and the scheduler path are not interchangeable for export without a MIDI file.** `WorkletSynthesizer.startOfflineRender()` is bit-identical to the library's real-time output and ~45× faster than real time, but it plays a *MIDI sequence* through the engine's own sequencer, not the tick timeline. The scheduler path can read the tick timeline directly and honour live edits, but it differs from the sequencer by a one-quantum dispatch phase and does not have the bit-identical guarantee. | ADR-0002 chooses the library's offline path for export, which means the export path needs a MIDI file built from the compiled timeline. That adds a writer to the export path and a second representation of the same arrangement. | Implement the SMF writer in P3 and have the export path consume it, so the tick timeline remains the single source of truth (D2). Verify with AT-6 that the exported WAV matches live playback. If the SMF writer slips, the documented fallback is to render the live path into an `OfflineAudioContext` with the same scheduler, giving up bit-identity but keeping one timeline. | P3 / P4 | Major | **Open — depends on the P3 SMF writer.** Recorded in ADR-0002 §Fallback. |
| **G-19** | **Only Windows was measured.** The engine is pure TypeScript, so the DSP is platform-independent, but the audio device, the render-quantum size and the scheduling behaviour differ per OS. The measured render quantum is 128 frames at 48 kHz; a platform with a different quantum changes the snapping arithmetic. | The timing criterion (NFR-TIM-1) is stated in frames, not milliseconds. A 512-frame quantum on some platform would make one quantum 10.7 ms, which changes the quantisation cost and the worst-case error. | Repeat the S1 driver on macOS and Linux (PulseAudio and PipeWire) and record the actual render quantum per platform in the report. The snapping helper takes the quantum size as a parameter, so no code change is expected — but the *measured* constants are Windows-only until then. | P1 | Major | **Open.** CI can run the driver headless on all three OSes (`xvfb-run` on Ubuntu, as the P0 smoke test does). |

| ID | Gap | Why it matters | Proposed resolution | Decide by | Severity | Status |
|---|---|---|---|---|---|---|
| **G-20** | **The end-to-end MIDI output jitter has not been measured on Linux.** Windows and macOS are closed: the CI workflow `.github/workflows/spike-s2-midi.yml` runs the loopback measurement on `windows-latest` (loopMIDI 1.0.16.27) and `macos-latest` (a CoreMIDI virtual endpoint), and the p99 jitter is **1.10 ms on Windows** (the typical case; 1.10–50.00 ms across the five runs, one driver stall) **and 0.10 ms on macOS**, with **0 late sends** in every configuration (idle, minimised, heavy UI load) across five CI runs per configuration (19 152 on Windows, 18 240 on macOS). | **G-21** | **The MIDI look-ahead window must exceed the worst main-thread stall.** With a 100 ms look-ahead, a renderer main thread that is blocked for 120 ms every 500 ms produced **32 late sends out of 912 (3.51 %)** with a p99 lateness of +14.27 ms. Chromium clamps a past timestamp to a zero delay, so a late dispatch is sent immediately and is audible early. With a 300 ms look-ahead the same load produced **0 late sends**. | A late dispatch is an audible timing failure, and NFR-TIM-2 explicitly requires that heavy UI activity must not audibly affect timing. The failure only shows up under load, so a naive test would miss it. | The production scheduler (P6) uses a look-ahead of at least 300 ms, and re-arms or re-schedules a message whose Worker tick was late. Add a regression test for "a late Worker tick must not produce a past-dated send" at the lowest possible layer (`src/midi`), and keep the S2 `--ui-load` run in the manual test checklist. | P6 | Major | **Open** — decided in ADR-0003 (≥300 ms window); the production implementation is P6 work |
| **G-22** | **Chromium's Windows MIDI backend does not report a removed device.** The S2 hot-plug probe removed the loopMIDI port from the OS while the app was running: the OS confirmed the removal (enumerating the ports outside Electron through RtMidi showed only the Microsoft GS Wavetable Synth), but Chromium's renderer kept listing the port and emitted **no `statechange` event**. Chromium's `MidiManagerWin::UpdateDeviceListOnTaskRunner()` only re-enumerates when Windows raises a device-change notification, and its own source notes that the raw device list may be updated before the MIDI driver's. On macOS the same probe removed the port cleanly and produced two disconnect events — every one of the three macOS hot-plug runs recorded four `statechange` events (two connected, two disconnected), while all four Windows runs recorded only the two initial `connected` events. | NFR-REL-2 says "the port list refreshes and a vanished port is reported without breaking playback". On Windows the app cannot rely on `statechange` to do either half. A user who unplugs a USB interface would see a port that no longer works, with no explanation, unless the app detects the failure some other way. | The production port manager (P6) must not treat `statechange` as the only signal: re-enumerate the ports when a send fails, when the MIDI settings are reopened, and on a slow poll while playing; treat a failed send as "the device is gone" and report it. `ResilientMidiSender` in the S2 spike already does the send-failure part. Add a regression test for "a failed send marks the port gone and triggers a re-enumeration" at the lowest possible layer (`src/midi`). | P6 | Major | **Open** — found by S2 (2026-11-05); the Chromium limitation cannot be fixed in the app, only worked around |
| **G-23** | **A single CI run is not evidence of a p99, and the measured p99 includes the driver, not only the app.** The S2 report originally quoted one CI run. Aggregating five runs per configuration (37 392 sends) changed three published numbers: the Windows jitter p99 is 1.10 ms *typical* but **1.10–50.00 ms** across the runs; the native candidate is late on **47.4–53.0 %** of Windows sends and **75.4–83.6 %** of macOS sends, with a received p99 jitter of **1.15–369.53 ms** on Windows; and macOS had four native runs, not five. Separately, the *received* error is the app's error **plus the loopback driver's own scheduling** — one Windows run had the driver deliver a bar 51 ms late while the app dispatched it 96.4 ms early. | Any published jitter figure taken from one run on a shared CI runner is a best case presented as a result. It also silently conflates the app's contribution with the driver's, so a reader cannot tell an app defect from a driver stall — and cannot tell the native path's genuine failure from a lucky runner. A p99 is a statement about a distribution; one sample of it says nothing. | Every published spike figure states **the range and the number of runs behind it**, and the report's tables are cross-checked against the raw JSON reports rather than transcribed. The app's own contribution is reported separately as the **dispatch spread** (how early the app handed each message to the driver), which is the part the app controls; the received figure is reported with the driver's contribution stated. Apply the same rule to S1's remaining measurements and to any future spike. | P1 (all spikes), P6 | Major | **Open** — found by S2 (2026-11-06); the S2 report and ADR now follow the rule, but S1's figures and any future spike are not yet re-checked this way |

## 5. Spike-driven unknowns

| Unknown | Spike | If the answer is "no" | Result |
|---|---|---|---|
| Can the SoundFont engine accept future-timed events with sub-quantum accuracy? | S1 | Worklet-side event queue, or play through the engine's own sequencer from the compiled timeline; as a last resort evaluate FluidSynth-WASM | **Closed 2026-11-05 — YES.** `SpessaSynthProcessor.processMessage(msg, offset, { time })` dispatches on the first quantum whose clock has reached the target: 128 frames worst case with an arbitrary target, **0 frames** when the target is snapped to the 128-frame grid. ADR-0002 mandates the snap and requires the snapped target to be computed with the engine's own clock accumulation — the natural `currentTime + quanta * quantumSeconds` lands a few ULP high and is dispatched a whole quantum late (measured 128.00 frames against 0.00). Splitting the quantum instead was measured and rejected (−16.4 dB, audible). No worklet-side event queue and no use of the engine's sequencer is needed for live playback. |
| Can Web MIDI meet 5 ms p99 jitter on all OSes? | S2 | Native RtMidi-based addon behind the same sink interface; document platform limitations | **Partly closed 2026-11-05 — YES on Windows and macOS; Linux not measured.** ADR-0003: **Web MIDI in the renderer**, with `@julusian/midi` (MIT, RtMidi 6.0.0) kept as an evaluated fallback. The end-to-end loopback measurement (the CI workflow `.github/workflows/spike-s2-midi.yml`) gives a **p99 jitter of 1.10 ms on Windows** (loopMIDI; 1.10–50.00 ms across the five runs, one driver stall) **and 0.10 ms on macOS** (a CoreMIDI virtual endpoint), with **0 late sends** in every configuration — idle, minimised window, and heavy UI load with a 300 ms look-ahead — across five CI runs per configuration (19 152 on Windows, 18 240 on macOS). The native candidate cannot match this on the same runners and the same loopback: RtMidi has no timestamped send, so **47.4-53.0 % of its sends on Windows and 75.4-83.6 % on macOS were late** (p99 lateness +14.79 ms on a busy machine); a native module also cannot load in a sandboxed preload and would need an IPC hop per message. Hot-plug was exercised by removing the loopback port mid-run: on macOS the port disappeared from the list and a `statechange` event reported it; on **Windows the removal works at the OS level but Chromium keeps listing the port and emits no event** (G-22). No send threw on either platform. The permission flow is verified: MIDI access is granted to the app's own origin by the session handlers, sysex is denied by default. Also measured: a 100 ms look-ahead produced 3.51 % late sends under a 120 ms main-thread block, while a 300 ms look-ahead produced none (G-21). **Still open (G-20):** the Linux end-to-end figure — the GitHub runners' Azure kernels ship without the ALSA sequencer drivers, so no virtual loopback can be created there. |
| Is any MP3 encoder licence-compatible and fast enough? | S3 | WAV only in v1.0 | **Closed 2026-11-06 — NO, but not for the expected reason.** Every npm-distributable JS/WASM MP3 encoder embeds a copyleft codec (`wasm-media-encoders` MIT/**LGPL LAME**, `@mediabunny/mp3-encoder` **MPL-2.0**/**LGPL LAME**, `@audio/encode-mp3` MIT/LGPL LAME, `@breezystack/lamejs` **LGPL-3.0**, `@toots/shine.js` **LGPL-2.0**, `@etercast/mp3` **GPL-3.0**), and the LGPL relinking condition is not demonstrable for a statically linked WASM/JS bundle (G-26). A wrapper's licence does not override the embedded codec's. **Speed was never the constraint**: every working candidate encoded 5 minutes of stereo audio in **under 10 seconds** (31×–107× real time). The only combined-permissive encoder found, `rusty_mp3` (Apache-2.0, pure Rust), also measured **best on quality** (SNR 35.2 dB at 128 kbps / 39.6 dB at 192 kbps, against 25.9/30.4 dB for the LAME builds) — but it has **no npm/WASM distribution** (G-25) and no listening test (G-24). MP3 **patents are not the blocker** (expired: EU/most jurisdictions by end-2012, US 2017-04-16, Japan 2017-04-23). ADR-0004: **v1.0 ships WAV only; no encoder enters `src/`.** |
| Do bundled fonts fit the size/load-time budget? | S4 | SF3 compression; fewer fonts; optional download of extra fonts after v1 | **Closed 2026-11-07 — YES.** A 64 MiB bundled asset packaged and loaded on all three operating systems: installers of **160.01 MB (Linux deb), 178.63 MB (Windows NSIS), 179.27 MB (macOS arm64 DMG), 182.96 MB (macOS x64 DMG) and 183.88 MB (Linux AppImage)**; installed sizes 420.48 MB (Windows), 337.46 MB (Linux), 323.03 MB (macOS arm64), 326.50 MB (macOS x64). First launch with the 64 MiB asset fetched over the custom protocol: **680 ms (macOS arm64), 1 390 ms (Windows), 1 764 ms (macOS x64)** — inside NFR-PRF-2's 5-second target. The Linux CI figure (5 483 ms) is dominated by Xvfb's first paint on a headless runner, not by the app: the renderer had loaded in 514 ms and the asset fetched in 241 ms (*the window-presentation time on a real Linux desktop is unverified*). **Budget set at 250 MB per installer and 500 MB installed** (ADR-0005): the Electron runtime alone is ~115 MB of a compressed installer, so the 150 MB originally suggested in OQ-11 was not reachable. **The recommended font set is ≈ 413 MiB as SF2 but ≈ 35 MiB as SF3** (measured by converting every bank with `sf2-cutter` 0.1.5 at Vorbis quality `0.4`); the SF3 figure is what fits the ~135 MB the budget leaves for assets. **The publishers' size figures could not be used**: the FreePats pages publish *archive* sizes, which are roughly half the real font sizes. Evidence: `docs/spikes/s4-packaging-report.md`, `docs/spikes/s4-soundfont-shortlist.md`. |
| Is macOS/Windows signing achievable without delaying release? | S4 | Unsigned interim builds with clear install notes | **Closed 2026-11-07 — YES, but it costs money.** macOS notarization needs an **Apple Developer Program membership at 99 USD/year** and an Apple-issued Developer ID certificate; there is **no free route** for an ordinary open-source project (only Apple's fee waiver for approved nonprofits, educational institutions and government entities). Windows signing: **Azure Artifact Signing at 9.99 USD/month** (cheapest viable), a public-CA OV certificate at 129–300 USD/year, or **SignPath Foundation at no cost** for qualifying OSI-licensed projects with manual per-release review. **EV certificates are not recommended** — Microsoft removed the EV OIDs from the Trusted Root Program in August 2024 and EV no longer buys a SmartScreen bypass. Linux needs no signature. **Decision (ADR-0005): the interim releases are unsigned**, the signing path is already in the build configuration, and the per-platform unsigned-install instructions are written (`docs/spikes/s4-packaging-report.md` §6), including the warning that Windows 11 Smart App Control blocks unsigned binaries with no per-app bypass. |

## 7. How gaps are closed

1. Decision made (by John or by spike result) and recorded in the gap's row (status → *Closed*, with date and one-line outcome).
2. Requirements or implementation docs updated; version bumped.
3. Matching tests added in testing.md and the progress.md decision log updated.
4. If a gap cannot be closed in its decide-by phase, escalate it in progress.md as a blocker.
